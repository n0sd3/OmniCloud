# S3 Gateway implementation plan

Goal: expose one user-scoped virtual bucket over SigV4 without another storage engine.
Architecture: Express protocol layer authenticates a gateway credential, maps keys to the virtual filesystem, stages verified bodies/parts on persistent disk, and calls shared upload/allocator/cache/adapters. Existing outbound S3Adapter is unchanged.
Spec: user's requirements and pre-edit architectural audit in conversation.

- [x] Write SDK integration tests and observe unsupported operations fail.
- [x] Add credential/session migrations; encrypted secrets; SigV4 verification using installed Smithy; XML errors/key validation.
- [x] Coordinate user mutations and sync; reuse overwrite/cache/upload with replayable staging; test old-content preservation.
- [x] Implement lists, streaming/ranges, writes, multipart with persistent parts, quota/TTL and restart recovery; run SDK tests.
- [x] Add user settings UI/API, env, health, Docker persistence and dedicated-host nginx configuration.
- [x] Test security/concurrency; run backend regression suite/frontend build; smoke-test real S3 clients; document exact limitations/results.

Constraints: no provider credentials exposed, no new provider implementation, bounded RAM, one backend process, serialized per-user mutations/sync, authenticated user on every lookup. Reject ambiguous duplicate keys instead of picking an arbitrary provider. Unsupported S3 operations must fail explicitly.

Rulings: user authorized implementation after the pre-edit audit; no extra approval/commit was needed. Reused installed Smithy/XML/CRC packages, declared directly. Persisted staging in the existing API data volume. Added shared per-user coordination and recovery backup promotion rather than a parallel storage implementation. First writes avoid unnecessary remote rename. Provider promotion is recoverable, not distributed atomicity.
